# 开发流程与学习方式

## 协作约定

- 开发助手在每个任务开始时说明业务问题、实现范围和验收方式。
- 小步实现，完成后说明改动、验证结果、局限及关键代码位置。
- 开发助手承担实现和排查工作，不要求学习者先独立掌握全部技术才推进。
- 学习者重点理解输入输出、业务约束、设计取舍和失败情形，并逐步参与小范围修改。
- 需要学习者决定的问题集中在业务偏好和重大范围变更；常规实现按既定约定推进。

## 一项功能的完整流程

1. 定义问题：谁在什么情境下遇到什么困难。
2. 写出输入、输出、边界与可验收示例。
3. 记录必要的设计取舍；影响架构的选择写入决策记录。
4. 在短期分支实现一个可演示的小功能。
5. 检查业务逻辑、错误处理、数据暴露和必要测试。
6. 更新相关文档，整理为便于审查的提交和 PR。
7. 检查通过后合并，形成可复现的阶段成果。

## Agent 开发约束

当前四 Agent 开发基线为需求 V1.1、Prompt 1.1.0，详见 [实现需求第 16 节](agent-implementation-requirements.md)。调用前使用 `validate_request` 校验结构化输入，调用后使用 `validate_result` 校验结果；通过后才可用于下游，不能只依靠 Prompt 约束。

Agent 之间使用 Agent Orchestrator 和结构化共享状态通信。禁止在 Agent 内部直接调用其他 Agent，也禁止把自然语言回复作为下游事实来源。

每个 Agent 的输出必须包含状态、计划指纹、事件版本、结构化事实或结果、证据引用和失败信息。候选方案通过后端保存的批次 ID 传递，正式计划发布只能由人工决策用例完成。

新增 Agent 时，先更新 [Agent 定义文档](agent-definitions.md)，再实现输入输出契约、编排条件、失败处理和测试。

GitHub 发布前先确认仓库根目录、许可证和公开内容。没有远程仓库时，先在本地记录任务和验收结果。

## 仓库与提交

- 使用独立项目仓库，避免把上级目录的其他项目和个人文件带入版本控制。
- 主分支保存可验证状态；功能分支示例：`feat/failure-impact`。
- 一次提交围绕一个清晰目的，避免无关格式变动与功能混合。
- 提交消息可采用 `feat:`、`fix:`、`docs:`、`test:` 前缀。
- PR 写清问题、最终行为、验证方法和已知限制；个人项目允许自行审查，但如实记录验证。

## 验证策略

- 调度核心：验证设备互斥、工序先后、资格、故障窗口和固定任务等不变量。
- 场景测试：固定输入验证故障影响、无可行方案及人工拒绝后计划不变。
- 状态流程：验证重复确认、过期版本、错误输入与发布失败。
- AI 部分：检查解释引用与结构化结果一致，不能由模型自行宣布排程可行。
- 界面：检查甘特图信息、交互状态和端到端演示；不把像素细节作为业务测试替代品。
- 文档等低影响变动只做必要检查，不为凑覆盖率编写测试。
- CI 随代码建立，执行约定的格式、静态检查和关键测试；未实际执行的检查不得写成通过。

## 面试展示材料

最终逐步补齐：运行说明、架构图、业务假设、固定演示数据、操作录像、关键决策记录、评估结果和已知限制。

指标必须写明样本、基线、运行环境与测量方式。不得将个人仿真结果包装为企业生产收益。

## 当前开发入口

主界面已迁移为 React + FastAPI，见 [ADR 0003](decisions/0003-react-fastapi.md) 和根目录 README 的双终端启动方式。前端项目在 `frontend/`，后端项目在 `backend/`，API 工厂为 `backend/src/sched_copilot/api/__init__.py`。内部依赖、职责和新增功能位置见 [代码结构与扩展规则](code-structure.md)。旧 Streamlit 已从当前实现移除，Git 保留历史。

在根目录运行前端命令 `npm --prefix frontend run format:check`、`npm --prefix frontend run lint:architecture`、`npm --prefix frontend test` 和 `npm --prefix frontend run build`；后端命令使用 `uv --directory backend run ruff check .`、`uv --directory backend run pytest` 和 `uv --directory backend build`。也可进入 `backend/` 后直接运行 uv 命令。CI 分别执行两组检查。业务规则不得搬到前端作为唯一校验，人工发布必须经过后端版本与约束校验。


## 紧急插单申请记录

业务员记录布局、审批节点语义和申请姓名兼容方案见 [紧急插单申请记录改造](insertion-request-tracking.md)。沿用现有审批流程与试排权限。

## 多设备故障并行处理

新版故障业务编号、稳定 `fault_event_id`、设备当天 `GZ` 序号和流程节点规则见 [多设备故障并行处理](failure-multi-event.md)。实现必须保留旧 `event_revision` 作为内部兼容字段，不得用全局最新 revision 推断其他事件已完成或历史化。

故障事件的并行处理、保存后生成修订号和流程驱动历史状态见 [多设备故障并行处理](failure-multi-event.md)。故障草稿不得写入事件历史；新事件不得仅因修订号更新而使未完成旧事件进入历史。
## LangSmith 与后台运行追踪

新增故障分析、插单评估的独立诊断记录：根运行关联本地 workflow/assessment、业务编号、计划版本、事件修订与输入指纹；四角色下记录规则工具、模型调用及适用格式修复，保存结果为独立节点。后台增加运行列表、业务类型/状态/日期筛选、节点详情和 LangSmith 跳转。旧记录不回填虚构 Trace。

追踪默认关闭；密钥仅在服务端配置。仅上传白名单身份、状态、耗时、模式、Token 和脱敏错误类别，不上传问题原文、生产快照、Prompt、模型原始响应。业务完成、降级与追踪上传状态分别记录；采用有界后台上传，追踪服务不可达不改变业务结果。沿用研发后台演示会话校验，不新增账号体系。

验收包括两类运行、规则/模型/降级、业务与保存失败、追踪上传失败、并发隔离、后台访问控制与旧记录兼容；全量后端及前端检查通过后，真实云端 Trace 仍需配置凭证并实测。本次不自动部署或上传历史数据。

实现入口：`application/telemetry.py` 提供请求内上下文；`telemetry_wiring.py` 在组合层包装规则工具和模型调用；`infrastructure/telemetry.py` 存储诊断并上传。故障 `/api/workflow` 与插单评估均覆盖四角色及保存节点，适用格式修复以实际模型调用与角色修复次数记录。手工调整、兼容分析和独立问答未纳入本版业务运行列表。

服务端配置（模板见 `backend/.env.example`）：

```dotenv
SCHED_TRACING_ENABLED=1
LANGSMITH_API_KEY=替换为服务端密钥
LANGSMITH_PROJECT=SchedCopilot
LANGSMITH_ENDPOINT=https://api.smith.langchain.com
```

默认 `SCHED_TRACING_ENABLED=0` 仅保存本地脱敏诊断；开启但无密钥显示“未配置密钥”。不需要启用 `LANGSMITH_TRACING` 等原生自动上传开关；模型请求显式关闭原生追踪，避免上传 Prompt 和原始响应。Endpoint 要求 HTTPS。密钥不进入页面、配置 repr 或诊断记录。

后台登录后查询 `/api/admin/traces`，支持 `kind`、`status`、北京时间日期 `start/end` 和 `page`，每页 20 条；详情为 `/api/admin/traces/{id}`。两者均要求现有研发会话并禁止缓存。详情提供服务器生成的 LangSmith 私有链接，需要对应 LangSmith 项目访问权限，不创建公共分享链接。上传后刷新可读取最新状态。

首次启动在现有 SQLite 中增建 `diagnostic_runs`，建表前调用现有 SQLite backup 机制；不回填旧业务记录。后台上传队列最多 32 条、一个工作线程、单请求超时 3 秒，上传失败不反复重试；队列满单独标记。队列是进程内的，重启不自动补传，历史“等待上传”不代表重启后仍在发送。诊断当前在业务调用结束后保存，后台不提供执行中的实时监控；业务页面沿用原有实时链路。部署时继续遵守备份和三方状态验收规范。
