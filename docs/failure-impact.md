## 业务目标

让计划员改变设备、发生时间、预计恢复时间与事件来源后，获得基于相同快照的影响范围和候选方案。事件录入、试算与正式计划发布是三个独立动作。

## 数据与边界

当前使用 2026-10-19 13:00、UTC+08:00 的仿真执行快照。此前工序已完成，之后工序尚未开工。不随系统时钟自动报工，也不能假定改变故障发生时间后执行状态会自动变化。

- 时间和来源有效时可以保存事件；事件质量问题会阻止试算，不会隐藏输入控件。
- 预计恢复未知可以保存，列出故障后原设备剩余任务的潜在风险，不计算精确延期，不生成候选。
- 故障涉及已开工/已完成工序时，提示人工处理在制品；首版不推断报废、断点续加工或迁移规则。
- 发生时刻之前仍标为计划中的任务，视为报工状态待核实，阻止试算。
- 只编辑一条当前故障事件，切换设备会替换它；不支持多个故障并存或累计约束。
- 接收时间采用仿真规则 `max(快照时间, 发生时间)`，数据库另存实际记录时间。不将仿真接收时间描述成真实设备上报。

## 状态流转

1. 修改输入：产生未保存草稿，清除当前页面的候选与 AI 分析，禁止发布旧结果。
2. 保存事件：校验基本字段，检查编辑所基于的事件版本，追加历史记录。正式计划保持不变。
3. 生成候选：使用当前计划和已保存事件，绑定计划指纹、事件指纹及递增的事件版本。
4. 比较方案：显示故障区间、工序前后变化、影响链及订单交期变化。
5. 人工决定：重新校验当前版本和约束，发布新计划或记录拒绝。

同一输入重复保存不会增加事件版本。事件从 A 改到 B 再改回 A，版本仍递增，因此 A 的旧候选不能再次发布。其他页面更新事件后，旧编辑器必须重新载入，不自动覆盖。

误操作恢复：左侧“恢复上次可试算事件”会按当前正式计划重新校验事件历史，选取最近一个可生成方案的事件；历史均不可用时尝试初始示例。恢复是追加事件版本，保留正式计划、人工决定和全部事件历史，同时清理未保存输入与旧候选。恢复后点击“生成候选方案”继续；不支持的业务约束仍不绕过。

## 影响口径

方案比较默认平铺：候选甘特图使用相同时间范围，工序调整和订单交付按方案横向对照，黄色标记方案间不同的安排。指标表绿色表示相对较优、红色表示较差，相同值不着色；各指标独立比较，不自动推荐或发布方案。影响链、证据与假设同时展开；人工确认区单独选择本次处理的方案。

- 直接影响：待加工工序的基线加工时段与故障窗口重叠，采用左闭右开的时间区间。
- 连锁影响：工序实际变化，且求解过程记录的前序等待/设备阻塞链能追溯到故障。
- 策略调整：工序发生变化，但记录中没有故障传导路径，单独标记，避免伪造因果。
- 直接影响计数不等于移动工序数；风险范围也不等于延期订单数。
- 订单表分别显示原完工、新完工、交期和新增延期。已经延期与新增延期分开呈现。

求解器记录被哪些工序或故障窗口阻塞，界面显示其中一条可追溯路径，不声称穷尽所有因果路径。没有直接影响时保持全部原计划任务，避免借故障触发无关重排。

### 主流程与采纳入口

当前故障的“查看 AI 分析详情”及“查看AI评估详情”统一进入完整方案决策页，复用已有分析，不自动重新生成。当前故障已发布时，展示绑定原始基线的只读报告存档；历史故障的“查看历史 AI 分析”保留只读右侧抽屉。

产线员工录入并保存设备故障后，由排产员触发 AI 分析。系统输出同一快照下的报告和甘特图对比，区分非原线等待方案（如转移至合格设备）、原线等待方案，以及原线等待遇到当日最后班次、无法排入等无可执行候选情况。原线等待本身不等于不可用，是否可执行以约束检查为准。

甘特图候选卡片内分别设置“采纳此方案（等待恢复）”和“采纳此方案（转移设备）”；转移候选标注“⭐ AI 推荐”。采纳动作绑定卡片对应候选 ID，高亮所选方案，并进入原有人工确认表单，填写理由后提交管理者审批；已批准的对应候选可按原流程发布，不绕过审批。页面最底部右侧统一提供“都不满意，转人工手动排产”入口；当前执行计划仅作对照，不提供采纳按钮。

- 有可执行候选且排产员采纳：进入待提交审批，由排产员提交、车间管理者审批，再由排产员发布计划。
- 排产员不采纳：进入人工调整模式，不改变当前执行计划。
- 无可执行候选：明确说明瓶颈、影响和下一步；禁用采纳不存在方案的操作，提供人工调整入口。可保留无候选评估结论，但不得将其冒充可发布计划。
- 数据缺失、契约冲突或工具故障仍须明确报错并按现有规则阻断适用动作；人工兜底针对方案不可用和业务产能死角，不绕过真实数据问题或系统故障。

### 人工调整与业务状态

人工路径为“人工调整中 → 草案确认评估 → 待提交审批 → 待审批 → 已批准 → 已发布”。草案持久化状态为 `editing`、`ready_for_review`；确认评估是执行阶段，不另存 `evaluating` 状态。审批复用 `pending`、`approved`、`rejected`、`superseded`、`published`。AI 采纳路径从“待提交审批”汇入同一审批发布流程。后端业务状态与 Agent 节点状态分别建模，不根据报告文字决定路由。

| 阶段 | 操作与状态要求 |
| --- | --- |
| 分析完成、待决策 | 保存分析来源与候选可用性；排产员选择采纳或人工调整 |
| 人工调整中 | 开放草案甘特图拖拽；有候选时保留来源候选，无候选时基于当前计划创建草案并标识待解决冲突，不伪造 AI 候选 |
| 草案确认评估 | 排产员确认后，后端重新校验并计算差异、交期和风险，再调用大模型整理人工调整草案报告；评估期间不得提交旧报告 |
| 待提交审批 | 仅校验通过、报告与草案修订一致时允许排产员提交；生成报告不等于已经提交 |
| 待审批、已批准 | 管理者查看绑定草案和报告并批准或退回；退回后允许修订，修订后重新评估并提交 |
| 已发布 | 排产员执行受控发布，产生新的执行计划及最终报告；审批通过本身不改变计划 |

人工拖拽仅修改尚未开工的任务草案，不修改已完成或已开工工序。后端检查设备资格、加工时长、工序顺序、设备与模具资源冲突、故障窗口及班次等既有硬约束。无效调整返回具体冲突，保留可修正草案，不允许提交审批或发布。人工操作不能自动外推未知班次；加班建议只有在存在明确可用班次条件且校验通过后，才能成为可执行安排。

草案、人工变更和报告需要持久化并支持刷新恢复。草案绑定故障修订、计划版本、输入与基线指纹，具有独立修订号；报告和审批绑定具体草案修订。编辑已提交或已批准草案必须使旧审批不再适用于新修订，并重新评估、提交和审批。故障、生产条件或执行计划变化后，旧草案需重评，不能覆盖新计划。

### 人工调整 API 与契约职责（已实现）

| 接口职责 | 输入与输出要求 |
| --- | --- |
| `POST /api/fault-drafts` 创建人工草案 | 接收故障与计划快照、可选来源分析和候选引用，返回草案 ID、修订、状态及编辑范围 |
| `PUT /api/fault-drafts/{draft_id}` 保存人工调整 | 接收草案 ID、预期修订、工序调整和可选人工原因；保存结构化变更，返回新修订与约束问题，防止跨页面覆盖 |
| `GET /api/fault-drafts/latest`、`GET /api/fault-drafts/{draft_id}` 读取人工草案 | 返回当前草案、变更记录、校验与报告状态；前端刷新后恢复同一草案，不自动重跑模型 |
| `POST /api/fault-drafts/{draft_id}/confirm` 确认并评估草案 | 校验当前快照和草案修订，计算权威差异与风险，调用模型整理报告；校验不通过时保持可修正状态，通过后进入待提交审批 |
| 提交、审批与发布 | 复用并扩展既有入口，绑定方案来源、草案修订、报告及快照；发布前再次检查版本、约束和批准范围，重复请求不得重复发布 |

新增命令与响应信封使用严格 Pydantic 契约，部分既有计划、指标与模型记录仍沿用 JSON 对象结构，不宣称全部嵌套字段均已强类型化。业务规则放领域/工具层；人工闭环由 `orchestration/manual_faults.py` 协调，组合入口注入规则工具；API 路由不重写规则。模型没有草案写入、审批或发布权限。前端仅依据后端状态控制拖拽、确认、提交与发布；评估完成后进入同一审批流程，不因前端页面跳转默认已批准。

### 所有报告统一说明系统、模型与人工贡献

初次分析报告、人工调整草案报告、管理者审批报告、最终发布报告均须明确总结“大模型做了什么、人工调整了什么”。使用结构化记录生成事实，不从解释文字反推变更或业务状态。

| 报告部分 | 必须包含的内容 |
| --- | --- |
| 系统与模型工作 | 分别说明规则工具实际完成的校验、候选生成、指标和风险计算，以及大模型实际完成的分析重点选择、证据组织和总结解释；注明真实调用模式、降级与未验证条件，不将规则计算冒充大模型工作 |
| 人工排程调整 | 记录操作者（现有演示身份，不宣称正式认证）、时间、订单/工序、原设备与新设备、原起止时间与新起止时间，以及已填写的调整原因；不编造未填写原因 |
| 调整影响与风险 | 计算相对当前执行计划的差异、完工与延期影响；有来源 AI 候选时补充相对该候选的人工差异，无候选时明确比较对象缺失，不虚构 AI 原方案或收益；风险结论绑定计算证据 |
| 人工决策与当前结论 | 单独记录采纳、提交、批准/退回和发布操作；明确可执行性、剩余风险、待处理事项及当前状态，不把采纳或审批描述为排程修改或已经发布 |

未发生人工排程调整时，明确写“未进行人工排程调整，采用系统生成方案”；初次分析尚未决策时说明“尚未进行人工调整或采纳决策”。最终报告保留审批时的方案、变更和报告快照，补充真实审批与发布结果；后续重新解释不得覆盖当时审批依据。

人工调整确认后应调用大模型生成草案说明；模型不可用、超时或输出不合格时，保留确定性校验结果及规则报告，明确说明大模型本次未完成的工作。只要草案校验通过且规则报告齐全，可以继续提交审批。规则工具或数据库真实故障不得伪装成模型降级或伪成功。

### 2026-10-24：误录故障撤销与预警列表

- 排产员在当前或历史故障卡片选择“撤销”，确认后分别调用 `POST /api/event/cancel` 或 `POST /api/events/{revision}/cancel`，携带当前事件修订和计划指纹；过期请求拒绝执行。
- 撤销是物理删除：删除同设备、同发生时间的全部故障修订，以及引用该故障的工作流、候选、人工草案及审批记录，不再保留原始故障或分析证据。旧分析若把该故障作为附加停机窗口，也一并清理，必须重新分析。
- 已发布的生产安排、版本与发布元数据保留，不回滚执行计划；若撤销的是已发布故障，则移除该故障的关联证据和停机留痕。撤销不等于取消已发布的工序调整。
- 删除后推进技术修订，防止复用旧审批。无剩余有效故障时仅保存不含故障数据的技术空态标记，页面不显示故障结论；重启不补回示例故障。空态接口的 event 字段仅为兼容表单的占位值，不落库、不参与分析；以 event_cancelled 标识禁止计算，需先录入新故障。
- 预警列表按正常文档流排列，卡片自然撑高、不收缩，间隔 16px；长提示和多条历史卡片在预警区内部滚动。

当前执行计划甘特图的停机留痕与时间轴绑定已发布计划：`plan_publication.fault_traces` 从不晚于当前版本的发布证据提取故障快照。新故障的录入、修改或撤销不改变既有计划留痕；新故障仅在故障分析和候选对比中展示，发布后才纳入执行计划留痕。


### 班次容量不足时的原线排尾默认方案

设备故障候选中，等待恢复策略若仅因登记班次容量不足而失败，规则工具生成原线排尾顺延候选：受影响的待加工工序及其同订单后续工序排到原设备队尾，允许超出最后登记班次。此规则仅适用于故障方案与人工故障草案，不改变插单排程规则，也不新增或假定已批准的加班班次。

设备资格、实体模具占用、换型、故障窗口、订单工序先后和已开工/完成工序固定等约束仍须独立复核。超班作为明确风险进入候选限制、Agent 评估和解释，以及人工调整报告；不得标记为班次校验通过。实际班次仍是利用率计算分母。

该候选走校验→排产→评估→解释的正常链路，提供当前执行计划与排尾候选的甘特图对比。排产员采纳后提交管理者审批并发布；不采纳则进入人工甘特图调整、确认草案报告，再提交审批发布。审批与最终报告保留系统/模型工作、人工修改和超班/延期风险。既有无候选历史不会自动改变，需要重新生成分析。


### Copilot 辅助问答与重新生成

- “✨ 获取 AI 解答”调用独立的只读 `POST /api/copilot/ask`，传递当前事件修订、基线指纹、工作流 ID 与问题。服务端在请求前后核对快照与最新工作流，拒绝旧结果。
