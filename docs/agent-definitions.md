# Schedule Copilot Agent 定义

## 1. 设计原则

Schedule Copilot 使用四类独立 Agent，由 Agent Orchestrator 根据用户意图、数据状态和已有结果动态决定调用哪些 Agent 以及调用顺序。

四个 Agent 不是固定串行流程。常见情况下会先校验、再生成候选、再评估和解释；但解释校验失败、重新评估已有候选等场景可以只调用部分 Agent。

排产时间、设备分配、约束判断和指标计算由确定性规则工具完成。Agent 负责读取事实、组织分析、解释结果和协调任务。任何 Agent 都没有发布正式计划的权限。

## 2. Agent 总览

| Agent | 核心职责 | 是否可修改正式计划 | 主要依赖 |
| --- | --- | --- | --- |
| 数据校验 Agent | 检查输入数据、版本和业务约束 | 否 | 计划、订单、设备、模具、事件、报工 |
| 排产执行 Agent | 调用规则工具生成候选方案 | 否 | 通过校验的数据和排产请求 |
| 评估 Agent | 比较候选方案和交付风险 | 否 | 候选方案、指标、影响链、假设 |
| 解释 Agent | 面向计划员解释事实、差异和风险 | 否 | 校验、候选和评估结果 |

## 3. 数据校验 Agent

### 职责

- 校验订单、工序、设备、模具和故障事件数据。
- 校验时间格式、时区、版本指纹和事件修订号。
- 校验设备能力、模具族匹配、工序先后和故障窗口。
- 识别缺失数据、执行记录冲突和过期快照。

### 输入

- 当前正式计划快照
- 订单和工序
- 注塑机及模具族能力
- 故障事件和预计恢复时间
- 报工与执行记录

### 输出

```json
{
  "status": "passed | blocked | warning",
  "issues": [],
  "facts": [],
  "required_actions": [],
  "snapshot": "..."
}
```

### 权限

只读业务数据和校验工具，不生成候选，不修改数据，不发布计划。

### 调用条件

- 生成候选前通常必须调用。
- 用户修改事件、订单或设备信息后可以重新调用。
- 解释校验失败原因时可以单独调用。

## 4. 排产执行 Agent

### 职责

- 根据有效的校验结果选择需要执行的排产工具。
- 生成等待原设备恢复、转移到合格设备等候选方案。
- 记录规则工具返回的候选、约束结果和证据。
- 将候选批次交给后端持久化，供后续评估和人工决策使用。

### 输入

- 数据校验结果
- 当前正式计划
- 故障窗口
- 设备和模具能力
- 用户指定的排产请求或策略

### 输出

```json
{
  "status": "generated | failed",
  "candidates": [],
  "constraints_checked": [],
  "evidence": [],
  "assumptions": []
}
```

### 权限

可以调用确定性排产工具并生成候选，但不能自行计算并覆盖正式计划，不能发布方案。

### 调用条件

- 用户请求生成或重新生成候选时调用。
- 数据校验未通过时禁止调用。
- 仅查看已有方案或解释已有结果时不必调用。

## 5. 评估 Agent

### 职责

- 比较候选方案的交期、延期、移动工序和完工时间。
- 分析设备转移、模具换型、资源竞争和影响链风险。
- 区分事实、假设、风险和方案取舍。
- 输出可供人工决策的比较重点，不替用户选择方案。

### 输入

- 候选方案批次
- 正式计划
- 订单交期和优先级
- 工序变化和影响链
- 证据与业务假设

### 输出

```json
{
  "status": "evaluated | blocked",
  "metrics": [],
  "tradeoffs": [],
  "risks": [],
  "recommended_focus": []
}
```

### 权限

只读候选和评估工具，不能修改候选，不能修改正式计划，不能发布。

### 调用条件

- 候选生成后需要评估时调用。
- 用户切换比较指标或追问方案取舍时可以重复调用。
- 用户只查看当前计划时不调用。

## 6. 解释 Agent

### 职责

- 将校验、候选和评估结果转换成计划员能理解的说明。
- 解释工序为什么受影响、方案为什么产生差异。
- 引用订单、工序、设备、事件和计算结果作为证据。
- 明确区分事实、假设、风险和未知信息。

### 输入

- 数据校验报告
- 候选方案和工序变化
- 评估报告
- 用户问题

### 输出

```json
{
  "summary": "...",
  "facts": [],
  "assumptions": [],
  "risks": [],
  "decision_guidance": [],
  "citations": []
}
```

### 权限

只读所有上游结果和证据，不得修改任何排产结果，不得调用发布接口。

### 调用条件

- 用户主动提问时调用。
- 需要生成方案说明时调用。
- 校验失败时可以只解释失败原因。
- 已有候选和评估结果时可以单独重新解释。

## 7. 动态编排示例

### 生成候选方案

```text
用户请求生成方案
→ 数据校验 Agent
→ 校验通过
→ 排产执行 Agent
→ 评估 Agent
→ 解释 Agent（需要说明时）
```

### 校验失败

```text
用户修改故障时间
→ 数据校验 Agent
→ 校验失败
→ 解释 Agent
```

排产执行 Agent 不得在校验失败时运行。

### 解释已有结果

```text
用户询问“O1002 为什么延期”
→ 读取已有候选和评估结果
→ 解释 Agent
```

不需要重新执行排产。

### 重新评估

```text
用户切换比较维度
→ 评估 Agent
→ 解释 Agent（需要文字说明时）
```

## 8. 编排器要求

Agent Orchestrator 必须：

1. 根据用户意图和当前状态选择 Agent，不写死全流程顺序。
2. 检查依赖结果是否存在、是否通过以及是否属于当前计划版本。
3. 在事件或正式计划变化后使相关结果失效。
4. 记录每次调用的 Agent、输入快照、工具调用、输出状态和失败原因。
5. 不向 Agent 暴露发布正式计划的工具。
6. 对模型失败、超时、空输出和无证据输出进行降级处理。

## 9. 后续开发验收标准

- 四个 Agent 有独立的输入、输出和测试。
- 数据校验 Agent 能阻止无效数据进入排产执行 Agent。
- 排产执行 Agent 只能调用确定性规则工具。
- 评估 Agent 不重复计算排产结果。
- 解释 Agent 的数字和结论可以追溯到结构化证据。
- 编排器可以根据场景跳过不需要的 Agent。
- 任一 Agent 失败时，其他无依赖的功能仍能正常使用。
- 所有 Agent 都不能直接发布正式计划。
