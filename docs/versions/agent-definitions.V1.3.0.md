## 1. 设计原则

Schedule Copilot 使用四类独立 Agent，由 Agent Orchestrator 根据用户意图、数据状态和已有结果动态决定调用哪些 Agent 以及调用顺序。

四个 Agent 不是固定串行流程。常见情况下会先校验、再生成候选、再评估和解释；但解释校验失败、重新评估已有候选等场景可以只调用部分 Agent。

排产时间、设备分配、约束判断和指标计算由确定性规则工具完成。Agent 负责读取事实、组织分析、解释结果和协调任务。任何 Agent 都没有发布正式计划的权限。

## 2. Agent 总览

| Agent | 核心职责 | 是否可修改正式计划 | 主要依赖 |
| --- | --- | --- | --- |
| 数据校验 Agent | 检查输入数据、版本和业务约束 | 否 | 计划、订单、设备、模具、事件、报工 |
| 排产执行 Agent | 调用规则工具生成候选方案 | 否 | 通过校验的数据和排产请求 |
| 评估 Agent | 比较候选方案和交付风险 | 否 | 候选方案、指标、影响链、假设 |
| 解释 Agent | 面向计划员解释事实、差异和风险 | 否 | 校验、候选和评估结果 |

## 2.1 Agent 通信方式

四个 Agent 通过 **Agent Orchestrator + typed shared state（结构化共享状态）** 通信，不直接互相调用。

```text
用户请求
   ↓
Agent Orchestrator
   ↓
结构化工作流状态
   ├── 数据校验 Agent
   ├── 排产执行 Agent
   ├── 评估 Agent
   └── 解释 Agent
```

Agent 的通信载体是带版本和来源的结构化结果，不是未经约束的自然语言。例如：

```json
{
  "agent": "validation",
  "status": "passed",
  "snapshot": "plan-fingerprint",
  "event_revision": 3,
  "issues": [],
  "facts": [],
  "evidence_refs": []
}
```

候选方案和完整证据保存在后端，后续 Agent 通过 `candidate_batch_id`、`candidate_id` 和 `evidence_refs` 引用，避免在 Agent 之间复制未经校验的大段文本。

通信约束：

- Agent 不直接调用其他 Agent，由编排器决定调用顺序。
- 每个结果必须包含状态、计划指纹、事件版本和证据引用。
- 过期或版本不匹配的结果不能被下游 Agent 使用。
- Agent 失败、超时、空输出和无证据输出都必须写入状态。
- Agent 不拥有发布正式计划的通信权限。

当前本地实现使用 LangGraph `StateGraph` 管理工作流状态。后续接入实时事件流时，可以在不改变 Agent 契约的前提下，将状态持久化或接入消息队列。

## 3. 数据校验 Agent

### 职责

- 校验订单、工序、设备、模具和故障事件数据。
- 校验时间格式、时区、版本指纹和事件修订号。
- 校验设备能力、模具族匹配、工序先后和故障窗口。
- 识别缺失数据、执行记录冲突和过期快照。

### 输入

- 当前正式计划快照
- 订单和工序
- 注塑机及模具族能力
- 故障事件和预计恢复时间
- 报工与执行记录

### 输出

```json
{
  "status": "passed | blocked | warning",
  "issues": [],
  "facts": [],
  "required_actions": [],
  "snapshot": "..."
}
```

### 权限

只读业务数据和校验工具，不生成候选，不修改数据，不发布计划。

### 调用条件

- 生成候选前通常必须调用。
- 用户修改事件、订单或设备信息后可以重新调用。
- 解释校验失败原因时可以单独调用。

## 4. 排产执行 Agent

### 职责

- 根据有效的校验结果选择需要执行的排产工具。
- 生成等待原设备恢复、转移到合格设备等候选方案。
- 记录规则工具返回的候选、约束结果和证据。
- 将候选批次交给后端持久化，供后续评估和人工决策使用。

### 输入

- 数据校验结果
- 当前正式计划
- 故障窗口
- 设备和模具能力
- 用户指定的排产请求或策略

### 输出

```json
{
  "status": "generated | failed",
  "candidates": [],
  "constraints_checked": [],
  "evidence": [],
  "assumptions": []
}
```

### 权限

可以调用确定性排产工具并生成候选，但不能自行计算并覆盖正式计划，不能发布方案。

### 调用条件

- 用户请求生成或重新生成候选时调用。
- 数据校验未通过时禁止调用。
- 仅查看已有方案或解释已有结果时不必调用。

## 5. 评估 Agent

### 职责

- 比较候选方案的交期、延期、移动工序和完工时间。
- 分析设备转移、模具换型、资源竞争和影响链风险。
- 区分事实、假设、风险和方案取舍。
- 输出可供人工决策的比较重点，不替用户选择方案。

### 输入

- 候选方案批次
- 正式计划
- 订单交期和优先级
- 工序变化和影响链
- 证据与业务假设

### 输出

```json
{
  "status": "evaluated | blocked",
  "metrics": [],
  "tradeoffs": [],
  "risks": [],
  "recommended_focus": []
}
```

### 权限

只读候选和评估工具，不能修改候选，不能修改正式计划，不能发布。

### 调用条件

- 候选生成后需要评估时调用。
- 用户切换比较指标或追问方案取舍时可以重复调用。
- 用户只查看当前计划时不调用。

## 6. 解释 Agent

V1.1 首版采用结构化模板解释已有结果，支持校验阻断、候选变更和评价取舍。用户问题用于识别比较意图及已有订单、工序，不作为事实来源。自由问答模型、API 和页面接入后续实现；首版仍遵守以下职责和权限边界。

### 职责

- 将校验、候选和评估结果转换成计划员能理解的说明。
- 解释工序为什么受影响、方案为什么产生差异。
- 引用订单、工序、设备、事件和计算结果作为证据。
- 明确区分事实、假设、风险和未知信息。

### 输入

- 数据校验报告
- 候选方案和工序变化
- 评估报告
- 用户问题

### 输出

```json
{
  "summary": "...",
  "facts": [],
  "assumptions": [],
  "risks": [],
  "decision_guidance": [],
  "citations": []
}
```

### 权限

只读所有上游结果和证据，不得修改任何排产结果，不得调用发布接口。

### 调用条件

- 用户主动提问时调用。
- 需要生成方案说明时调用。
- 校验失败时可以只解释失败原因。
- 已有候选和评估结果时可以单独重新解释。

## 7. 动态编排示例

### 生成候选方案

```text
用户请求生成方案
→ 数据校验 Agent
→ 校验通过
→ 排产执行 Agent
→ 评估 Agent
→ 解释 Agent（需要说明时）
```

### 校验失败

```text
用户修改故障时间
→ 数据校验 Agent
→ 校验失败
→ 解释 Agent
```

排产执行 Agent 不得在校验失败时运行。

### 解释已有结果

```text
用户询问“O1002 为什么延期”
→ 读取已有候选和评估结果
→ 解释 Agent
```

不需要重新执行排产。

### 重新评估

```text
用户切换比较维度
→ 评估 Agent
→ 解释 Agent（需要文字说明时）
```

## 8. 编排器要求

Agent Orchestrator 必须：

1. 根据用户意图和当前状态选择 Agent，不写死全流程顺序。
2. 检查依赖结果是否存在、是否通过以及是否属于当前计划版本。
3. 在事件或正式计划变化后使相关结果失效。
4. 记录每次调用的 Agent、输入快照、工具调用、输出状态和失败原因。
5. 不向 Agent 暴露发布正式计划的工具。
6. 对模型失败、超时、空输出和无证据输出进行降级处理。

## 9. 后续开发验收标准

- 四个 Agent 有独立的输入、输出和测试。
- 数据校验 Agent 能阻止无效数据进入排产执行 Agent。
- 排产执行 Agent 只能调用确定性规则工具。
- 评估 Agent 不重复计算排产结果。
- 解释 Agent 的数字和结论可以追溯到结构化证据。
- 编排器可以根据场景跳过不需要的 Agent。
- 任一 Agent 失败时，其他无依赖的功能仍能正常使用。
- 所有 Agent 都不能直接发布正式计划。

## 10. V1.3 设计：设备故障场景的 Agent 内部质量闭环

**稳定引用 ID：`AGD-V1.3-D1`**
**状态：已确认设计；原始设计存档，当前实现与差异见第 11 章。** 本章优先级高于前文未涉及质量循环的概念流程；若与现有 V1.1/V1.2 实现记录有冲突，以当前已实现代码为事实，以本章作为后续开发设计。

### 10.1 目标与范围

本设计要求每个 Agent 在把结果交给下游前，执行“产生结果 → 独立检查 → 针对问题修正 → 再检查”的有限闭环。检查不通过不能只靠模型自我声明通过。

本版本只覆盖单一设备故障事件、已知恢复时间、现有演示生产数据及两种现有排产策略。未知恢复时间、缺失生产数据、输入版本过期等作为阻断或降级测试；本版本不新增插单、缺料、多个同时故障及新的排产策略。

质量闭环的目的在于发现、处理并披露可检查的问题，不承诺找到全局最优排产。**合法但收益一般的方案仍可交付；违反硬约束的方案不可作为可发布候选交付。**

### 10.2 统一执行契约

每个 Agent 的一次运行应记录：

- `agent_id`、需求版本、规则/校验器版本、输入快照指纹和依赖结果引用；
- 当前轮次、执行的业务工具、初始输出和质量检查结果；
- 每个问题的稳定代码、严重级别、证据引用、是否可修正；
- 修正动作或停止原因、最终状态、是否允许交给下游。

质量检查器是 Agent 之外的可信边界：硬约束和数值一致性由确定性代码检查；模型可协助筛查解释覆盖度或提出允许范围内的调整，但不能自行裁定事实、放宽硬约束或宣告规则检查通过。最终状态至少区分 `passed`、`warning`、`blocked`、`failed` 和 `degraded`，其中 `warning` 不能被呈现成完整通过。

循环上限为 **每 Agent 最多 3 轮（含首次执行）**。只有存在具体、可修正的问题才进入下一轮。以下任一情况发生时停止：通过质量门、问题属于不可修正的数据缺失/硬冲突、到达轮次或总时限上限、输出与上一轮重复且未改善、业务工具失败。停止时保留最后一次有效报告和停止原因；失败尝试不得覆盖有效结果。

内部修正不得改变输入快照。若业务数据、事件版本或正式计划指纹变化，立即使本次运行及依赖输出失效，要求从校验重新开始。禁止以重试掩盖并发版本冲突。

### 10.3 各 Agent 质量门

#### 10.3.1 数据校验 Agent

**质量门：**

- 对当前故障场景适用的必检项有明确执行记录，至少覆盖输入及版本有效性、设备存在、故障开始/恢复时间关系、排产依赖、设备/模具适配，以及本场景排产所需的班次和换型数据。
- 每项检查结果可区分通过、阻断、警告、未检查；未检查不能默认为通过。
- 阻断和警告均指向实际数据字段或证据，解释其对后续排产的影响。
- 缺少必需的恢复时间、班次或换型数据时，不得构造默认值或虚假指标。

**修正方式：**发现检查覆盖遗漏时，可在同一输入快照下补执行确定性检查，最多计入 3 轮。真实业务数据缺失、非法或相互冲突时，不循环生成数据；输出 `blocked`，列出需要补充或确认的字段。

**下游放行：**只有硬性必检全部执行且没有阻断项才允许调用排产 Agent。带警告继续时，必须有明确降级规则，且警告与限制随结果传递。

#### 10.3.2 排产执行 Agent

**质量门：**

- 必须生成约定策略所要求的候选数；候选身份和策略标签不能重复或错配。
- 对每个候选独立验证工序唯一性/完整性、依赖顺序、机器能力、故障停机窗口、班次、换型准备时间和模具占用等本场景硬约束。
- 排产时间线与结构化工序数据一致；方案证据能说明相对于正式计划发生的变化及其原因。
- 无合法候选时不得生成可发布候选；不得因模型判断“看起来合理”跳过验证。

**修正方式：**对可调整的策略或设备分配问题，模型只可从系统给定的有限策略/决策选项中提出调整；规则排产工具重新生成，独立校验器复核。模型不得直接改写开始/结束时间、时长或校验结论。硬约束失败可尝试定向调整，最多总计 3 轮；每轮完整运行候选生成和硬约束校验。某策略仍无合法候选时，明确记录该策略失败；如果另一策略合法，可将其作为部分结果交给评估，并显示候选不完整。

**交付门：**只有通过硬约束的候选可以登记为可评估/可发布候选。三轮后仍不合法则 `blocked`，失败候选不进入比较或发布接口。合法候选即使交付风险较高，也交由评估 Agent 如实量化，不以软指标低为由伪称硬约束失败。

#### 10.3.3 评估 Agent

**质量门：**

- 所有有效候选均被评估，且指标均由确定性评估工具从对应候选重算，不复用模型生成数字。
- 指标的输入候选、基准计划、时间范围和单位一致；逐项指标可追溯至证据。
- 换型次数/分钟、设备利用率、完成/延期等仅在所需数据完整时输出；数据缺失则列入 `missing_metrics` 并解释，禁止零值替代未知值。
- 派生指标与源数据可复算，候选缺失、版本过期或证据不匹配均视为未通过。

**修正方式：**遇到计算或引用不一致，先检查证据映射并调用确定性工具重新计算，最多 3 轮；禁止让模型修补指标数值。缺少源数据时以 `warning` 降级并逐项说明，不能通过重算消除真实缺失。无法验证候选归属或输入快照时 `blocked`。

**下游放行：**只允许将已验证指标和明确缺失项交给解释 Agent；任何未校验的模型估算不得进入正式评价结果。

#### 10.3.4 解释 Agent

**质量门：**

- 每个事实、时间、数值和方案比较均可由当前版本证据引用；引用存在且属于同一候选批次和输入快照。
- 结论与规则输出一致，正确区分事实、假设、风险、限制及建议，不把相关性说成因果。
- 说明故障是否直接影响该工序；设备转移说明原设备故障状态、可选设备资格及可验证的开工时间差，不将主动优化描述成故障强制转移。
- 必须披露缺失指标、上游警告/降级及未验证项目；不得将不完整评估表述为全面结论。
- 文字时间使用面向用户的本地时间表达，不输出不必要的时区偏移后缀。

**修正方式：**由独立的结构/引用检查器发现遗漏或不一致时，向模型提供具体问题及允许引用的证据，请其只修正解释文字；修正后重新做相同检查，最多 3 轮。事实证据自身冲突时不得让模型选择相信哪一条，返回 `blocked` 或依据规则模板 `degraded`。

**失败出口：**模型输出仍不合格时，优先回退到由已验证证据生成的规则模板解释，并清楚标记“规则说明”；若规则模板也无法覆盖关键阻断事实，则不输出确定性结论，返回警告和证据项。

### 10.4 质量失败与工作流处理

| 失败位置 | 下游行为 | 用户可见结果 |
| --- | --- | --- |
| 校验阻断/必要数据缺失 | 不运行排产；解释 Agent 可解释已验证的阻断原因 | 阻断项、缺失字段及补充要求 |
| 所有排产策略均无合法候选 | 不运行候选评估，不产生可发布批次 | 无合法方案及违反的约束 |
| 仅部分策略产生合法候选 | 仅评估合法候选；明确本次方案不完整 | 每种策略通过/失败状态和原因 |
| 指标可计算但部分指标源数据缺失 | 仅将已验证指标交给解释 Agent | 指标值、缺失项及影响范围 |
| 解释模型检查失败 | 采用已验证规则模板或显式降级 | “规则说明/模型未通过检查”及原因 |
| 输入版本在执行中变化 | 丢弃该版本所有待交付结果并终止 | 版本冲突，要求重新载入并执行 |

质量重试只在当前 Agent 内进行；如果失败意味着上游输入有误，不在下游自愈。重做排产后必须重做评估和解释。质量循环不含正式发布；正式发布仍由人工明确选择已验证候选，并由后端重新检查版本及硬约束。

### 10.5 动态状态与审计展示

- 每个 Agent 展示状态：`待执行`、`检查中`、`修正中（第 n/3 轮）`、`通过`、`警告/降级`、`阻断`、`失败`。
- 每轮仅显示对用户有用的检查项、发现的问题、采取的修正及最终结果；不展示思维链或内部隐式推理文本。
- 显示必须由真实执行事件驱动；不得用预先播放的动画伪装 Agent 已经检查或重试。
- 最终报告可审计地关联 `workflow_id`、`agent_id`、轮次、输入指纹、工具结果引用、规则/提示版本和停止原因。日志不得记录密钥或不必要的完整敏感提示。
- “通过”表示本版本规定并实际执行的质量门通过；不得扩大解释为对真实工厂全部资源或未来结果的保证。

### 10.6 验收与故障注入

验收必须使用固定、可复现的设备故障数据，并包括成功路径及故障注入。至少覆盖：

1. 正常故障且恢复时间、班次、换型数据齐全：四个 Agent 均记录质量门结果；排产候选硬约束通过；评估指标复算一致；解释引用有效。
2. 注入一个可修正的排产输出违规：检查器检出明确违规，触发定向重排；后续候选通过独立复检，旧失败候选不可发布。
3. 注入始终无法修正的硬约束违规：三轮内停止；状态阻断；无可发布候选。
4. 缺少恢复时间：校验阻断；无排产和虚构时间；只返回可验证的阻断解释。
5. 缺少换型或班次数据：缺失项明确；相关排产或指标按规则阻断/降级，不伪造零值、可用时段或通过状态。
6. 篡改评估指标或引用：评估质量门检出并由工具重算；若来源仍不足则披露缺失，不接受模型修补数字。
7. 解释虚构时间/指标、错引候选或漏报已知警告：检查器拒绝并给出具体项；修正后复检，超限回退规则说明或失败。
8. 在某轮改变输入事件/计划版本：旧结果整体失效，工作流停止，候选不得进入比较或发布。
9. 所有重试达到上限、出现重复输出、超时或工具异常：停止原因确定且对用户可见，不无限循环，不声称通过。
10. 人工发布路径：仅可发布服务端保存、当前版本且通过排产硬约束的候选；质量重试本身不会改正式计划。

每项验收都应断言业务状态、候选可用性、结构化质量事件及正式计划是否保持不变；仅断言 Agent 文本包含“通过”不算验收。


## 11. V1.3.0 实现：有界输出质量闭环

**稳定引用 ID：`AGD-V1.3-I1`**

**设计来源：`AGD-V1.3-D1`（V1.3-draft.1）**

本章描述实际代码行为；第 10 章仍保留作为设计依据，不能将尚未实现的设计选项当作已实现能力。此版用户已授权开发。

### 11.1 内部执行与检查

四个 Agent 各自调用共享 `agents/quality.py` 的有界循环；编排器只负责依赖、进度与交付前契约复核，不重新执行整个 Agent 充当修正。

| Agent | 检查 | 修正动作 |
| --- | --- | --- |
| 数据校验 | 证据版本、快照一致性，以及完整规则检查结果的覆盖、问题、限制 | 在原快照上重新执行标准校验，重建报告与证据，不补造业务数据 |
| 排产执行 | 独立硬约束校验、工序与变更记录，完整候选、策略和风险披露与标准规则结果一致 | 从原快照及允许策略重建候选和约束证据；旧失败输出不登记 |
| 方案评估 | 独立重算指标并比对全部指标、差异、风险、缺失项和证据 | 重算并重建整份评估，不让模型修补数字 |
| 结果解释 | 全部内容与当前证据生成的受控模板一致，包含风险、限制及人工确认要求 | 从当前证据重新生成受控模板并复检 |

每轮执行器只收到输入副本。修正器收到拒绝的输出及结构化检查问题，执行上表中确定的重建动作。修正后必须通过相同检查，才允许交给下游。合法报告中的业务警告仍然保留，不靠重试消除真实数据缺失。

### 11.2 停止与失败交付门

- 每个 Agent 最多 3 轮，含首次；相同失败输出重复出现则提前停止。
- 内部规则工具循环预算为 120 秒，在工具和检查返回时核对；超时输出丢弃。同步工具无法被该循环强制中断，模型调用时限仍由原模型配置控制。
- 过期证据、证据冲突、工具检查了其他输入快照，不执行修正。
- 工具运行异常不自动重试；缺恢复时间或无可行候选等业务阻断保留明确错误。
- 未通过的工具结果不合并进证据目录；失败报告不携带可供下游使用的候选或指标。依赖它的 Agent 停止，完整工作流失败时不返回可发布候选。
- 质量元数据写入 `quality`：实现版本、最终状态、轮次、每轮问题与修正动作、停止原因。输入快照、规则版本和结果引用继续使用既有请求、证据与工作流字段。
- 前端消费真实 `quality_phase`、`quality_checked` 事件，显示执行/检查/修正轮次；详情展示每轮问题及动作。修正不计作新的工作流节点。

### 11.3 与设计的边界及后续扩展

- 此版实现确定性输出质量闭环；模型仍只选择有证据支持的分析重点。没有新增模型自主改策略、自由改写解释或标准 ReAct 推理循环。
- 设计中的模型有限策略调整、模型文字修正是后续扩展项。当前固定使用已允许策略重建和受控模板，比对及修正权限均不交给模型。
- 模型辅助失败仍用既有 `execution.mode=fallback` 和错误码说明；质量结果用 `passed/warning/blocked/failed`，没有新增独立 `degraded` 业务状态。
- 未新增插单、物料短缺或发布权限；正式发布继续走人工决定与服务端版本/约束检查。

### 11.4 自动验收入口

- `backend/tests/unit/test_quality.py`：问题反馈、修正复检、轮次上限、重复输出、过期证据、工具异常、总时限、进度隔离。
- 各角色测试：校验覆盖遗漏、坏引用、伪造通过记录、变更不一致、指标篡改、解释虚构/漏报风险，以及修正后与可信结果一致。
- `backend/tests/unit/test_orchestration.py`：修正和复检先于下游开始；修正失败不泄漏候选证据、不继续下游。
- 既有 API/生产演示/发布测试继续验证：缺失数据警告、版本冲突、真实生产约束、人工发布边界。
- 前端流式交互测试验证新质量事件不会误记为节点完成，执行详情显示真实轮次与修正记录。浏览器视觉验收不以单元测试替代。
