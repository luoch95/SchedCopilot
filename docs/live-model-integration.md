# 四 Agent 主流程模型接入（V1.2）

## 执行方式

`POST /api/workflow` 的生成、仅校验、重评估、解释四种意图保持不变。编排器按当前状态选择角色，每个实际执行的角色最多发出两次模型请求：

1. 模型调用 `run_<role>_tool`，参数必须为空。后台执行既有 Agent，计算并独立校验真实结果。
2. 后台按问题检索最多 24 条完整事实，总文本不超过 8000 字符；不截断单条事实。模型调用 `submit_focus`，选择并排序最多六条事实编号。

模型不生成计划、计算指标、修改业务状态或决定发布，也不改变确定性路由。原角色报告、风险、假设、缺失指标完整保留；模型重点属于附加展示，不能覆盖原报告。当前尚不允许自由改写事实，复杂问题在既有事实范围内筛选相关内容。

模型只能收到本角色事实文本及当前上下文，不能指定文件、URL 或任意业务工具。选择结果须符合严格结构，编号存在且不重复，显示的文本和引用由服务器取回。用户问题及工具事实均作为数据处理；模型要求发布或修改输入会被拒绝并回退。

## 配置

项目根目录 `.env` 自动加载，已设置的终端环境变量优先。参照 `backend/.env.example`：

| 配置 | 用途 |
| --- | --- |
| `LLM_API_KEY` | 后台密钥 |
| `LLM_MODEL` | 供应商提供的实际模型名称 |
| `LLM_BASE_URL` | 兼容 API 地址；OpenAI 官方地址可留空 |
| `SCHED_WORKFLOW_MODEL_MODE` | `auto`、`live` 或 `rules` |
| `LLM_API_TYPE` | `chat_completions` 或 `responses` |
| `LLM_TIMEOUT_SECONDS` | 单次请求超时，默认 30 秒，范围 1–60 秒 |

`auto` 有密钥和模型即启用，否则保持规则模式。`live` 缺少配置时也披露 `MODEL_NOT_CONFIGURED` 回退。`rules` 不构造模型客户端。修改配置后重启后端。

兼容供应商对工具参数支持可能不同，因此不发送强制指定名称的 `tool_choice`，后台严格检查实际返回的工具名、参数、数量和选项。需要 Responses 工具调用的 OpenAI 模型使用 `responses`；其他供应商按其接口能力配置。每个请求限制输出 4096 Token，不自动重试；不硬编码模型名称、供应商价格或预计费用。

接口实现参考 [OpenAI 官方工具调用文档](https://platform.openai.com/docs/guides/function-calling)。

## 结果与回退

`trace[].execution` 新增字段，规则模式为 null：

| 字段 | 含义 |
| --- | --- |
| `mode` | `live` 或 `fallback` |
| `model` | 配置的模型名称 |
| `calls` | 尝试请求数，最多 2 |
| `input_tokens` / `output_tokens` | 已返回的用量之和；无用量时为 null，不代表免费 |
| `elapsed_ms` | 本角色模型与工具的总耗时 |
| `error_code` | 安全错误码，成功为 null |
| `prompt_sha256` | 实际模型系统提示词的哈希，包括工具模式指令 |
| `highlights` | 服务器校验并取回的完整文本及证据引用 |

缺配置、超时、鉴权失败、限流、API 错误、无效模型输出分别记录安全错误码，不输出原始异常、密钥或未校验文本。第二次模型请求失败时复用已经计算的结果，不重复执行工具；工具本身失败则继续保留 failed，不能用模型成功掩盖。

页面在每个角色下标注“模型辅助”或“规则回退”，回退时显示总提示。辅助分析增加“本次分析重点”，完整事实、风险、假设及人工确认流程不变。执行详情显示请求数、耗时、已返回 Token 和错误码。

## 版本与验证

本扩展的需求版本为 V1.2；四角色结构化输入输出仍兼容 V1.1，Prompt 文件及规则 Agent 的元数据维持 1.1.0/V1.1。模型适配层不修改这些报告，只扩展工作流 trace。旧三角色 `/api/analysis` 不属于当前前端主流程。

自动测试强制工作流规则模式，模型边界测试注入模拟供应商，覆盖四角色工具、越权发布、篡改参数、越界/重复重点、超时、缺配置、过期上下文和 HTTP 后续意图。真实供应商调用另行手动验证，不作为普通 pytest 的一部分。

模型运行信息仅在本轮响应中返回；业务工作流状态保存在内存会话中。尚未实现模型调用记录的持久化审计、金额计费或多案例模型效果评测。

## 插单试排链路（URG-LLM-01，2026-10-20）

`POST /api/sales/requests/{request_no}/assessment` 复用上述模型配置，四阶段依次完成规则校验、确定性试排、指标复核和解释，再分别调用一次模型筛选本阶段的重点。模型只调用 `submit_focus`，每阶段最多选择六条服务器事实；本链路不使用故障流程的 `run_<role>_tool` 协议。模型作用是选择和排序已有事实，不自由生成排产结果或改写报告。

每次试排正常共四次模型请求。任一阶段超时、接口失败或输出不合法，该阶段及后续阶段回退规则，不继续请求供应商；已成功阶段仍保留其重点。业务规则校验失败照常阻断，不能由模型回退绕过。单次超时沿用 `LLM_TIMEOUT_SECONDS`，该接口仍同步返回，四次调用可能增加等待时间。

返回的 `workflow.mode` 为 `rules`、`live` 或 `fallback`；`workflow.trace[].execution` 记录实际请求数、耗时、Token、提示词哈希、安全错误码和重点。每个阶段的模型请求只包含宏观事实及限长申请理由，不发送设备/模具/工序排布；返回文本由服务器按已校验 ID 取回。业务员仅渲染宏观数据，计划员仍可查看完整规则计算明细。

与上述故障链路的内存记录不同，插单的完整 `workflow` 随既有 `assessment_json` 保存到数据库，刷新和重启可恢复。历史规则试排保持原快照，接入后需要重新试排才会产生模型辅助记录。模型不审批、不发布，不改变执行计划。
