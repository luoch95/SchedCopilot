## 2026-10-19 / URG-05～08 / IMPL-05：插单流程闭环

- 本轮授权：业务员提交与试排 → 领导审批/驳回 → 计划员复核发布 → 各角色刷新后追踪最终状态。沿用现有三表和工作台，不新增开发文档。
- D-05：演示入口增加领导角色；角色声明仅用于演示流程校验，正式认证授权后续接入。
- D-06：领导审批绑定完整试排结果的指纹；重新试排或计划/事件/生产资源变化后，旧批准不可发布，须重新审批。申请不开放原地修改，需求变化重新提交。
- D-07：领导可批准有延期风险的有效试排，必须填写理由；审批不等于发布。计划员必须填写复核理由后显式发布；拒绝和发布均保留状态历史。
- 验收：提交、试排、审批、发布持久化；重复点击不重复发布；过期/越角色/未审批发布被阻止；发布版本递增，新增订单及模具资源在重启后仍可查询和继续排产；既有故障流程回归通过。
- 实施结果：演示闭环代码完成，未提交 Git。领导角色可填写理由批准/驳回；计划员在原工作台查看设备与工序、填写复核理由后发布；业务员只渲染宏观摘要。全部角色刷新可查看所有状态、审批意见和状态历史。
- URG-05：复用现有四 Agent 类，新增 run_insertion 入口，经 orchestration/insertion.py 调用 tools/insertion.py，执行输入校验、确定性试排、独立约束校验和指标重算、模板解释；完整 JSON 保存 trace 与解释。插单入口目前固定 rules 模式，不调用大模型，不沿用故障专用契约或模型配置。
- URG-06：POST /api/sales/requests/{id}/actions 接收 action（approve/reject/publish）、reason、assessment_id、operator_role。审批绑定完整试排 JSON 指纹。GET /api/sales/requests 现默认返回全部状态，?status=pending_approval 保留原待审批筛选，也支持 approved/rejected/published。声明角色只做演示流程检查，可被伪造，不是正式认证授权。
- URG-07：发布在同一 BEGIN IMMEDIATE 事务更新 current_plan、production_inputs、decisions、申请状态和状态历史；版本加一。实体模具、已校验日历一并保存，已发布插单从现有三表恢复为正式订单；重启后可继续插单和既有故障排产。重复发布同一试排不增版本或日志。本轮提供复核后发布已批准方案，没有新增拖拽调整或插单多候选比较；改变结果须重新试排并审批。
- URG-08：保存试排、审批和发布事务检查计划/事件/生产资源版本；发布前重跑并核对结果，事务内再次核对防止并发变化。重新试排撤销原批准、回到待审批；旧页面操作不能批准/驳回/发布新试排。其他申请发布后旧批准必须重评重审。驳回/发布终态禁止再试排，需求变更新建申请。发布结果保留发布前评估快照。
- 回归修复：发布后故障策略可能得到相同结果、仅剩一个候选；自动生成流程改为解释唯一候选，避免误要求两个比较对象而阻断。显式比较请求仍要求足够证据。
- 测试：新增 backend/tests/integration/test_insertion_closure.py，覆盖完整链路、重启、后续插单、原四 Agent 故障流程、角色和状态限制、旧页面操作、计划/事件/资源过期、发布回滚、并发变化与另一申请发布使旧批准失效；前端覆盖领导会话恢复、审批回显、发布刷新、过期禁用。最终检查结果另记本节。
- 实际 HTTP：独立临时 SQLite、8011 后端，1000件申请通过提交→四角色规则试排→批准→发布→重复发布→停止全部测试进程→重启恢复，最终 published、V2，结果和新增订单均恢复。5173代理200，8000已重启加载新接口；原演示库保留2条申请，未新增或发布测试数据。
- 人工验收：业务员提交100件 P-DEMO-001并评估、刷新确认 → 领导展开同一申请填理由批准 → 计划员查看设备/工序、填理由复核发布 → 业务员刷新显示已发布、正式版本仅加一。另取批准申请改变故障后，旧结果应禁止发布；重试排后回待审批、重审后才可发布。
- 限制：演示角色非权限体系；只试排一条申请、只保存最新试排；精确评估绑定、无审批容差；无需求修改/撤回。浏览器连接仍报 sandboxPolicy 缺失，未完成实页点击与视觉验收，不将 HTTP/自动交互测试当作实页验收。

- 排程工具：`domain/insertion.py` 为独立确定性工具，不依赖 Agent、FastAPI 或数据库。先固定所有已开工/完成工序；优先安排插单，按原计划开始顺序安排其他未开工任务，不提前原有工序开工；逐个设备/班次真实间隙查找位置，检查设备能力、模具兼容、前后换型、实体模具跨设备占用、工序先后和现有停机窗口。换型也不得提前到演示快照之前。最后执行独立整体验证，再计算结果。
- 固定与变化边界：只试排单条申请，不叠加其他待审批申请；保持正式计划及原工序定义不变。派生插单订单 ID 为 URG-{申请UUID}，工序 ID 加 OP 序号；这只是试排引用，不表示已创建正式生产工单或已发布。
- 指标：预计完成时间取插单最后一道工序结束时间；是否满足交期按该时间与要求交期比较。受影响订单数仅统计原订单最终完成时间发生变化的订单，不包含插单自身，也不把工序调整但完工时间未变的订单计入。延期分钟数按正延期向上取整；延期变化=试排延期-原延期；延期加重订单数统计该变化大于0的原订单。
- 原基线限制：原演示计划未完整预留换型和停机窗口，因此结果以正式计划为比较基准时，变化也可能包含这些约束修正。结果保存 baseline_resource_issues，业务员显示通用说明，计划员可看具体校验项；不声称所有变化都是插单的净影响。
- 接口：POST `/api/sales/requests/{request_id}/assessment` 对已保存申请进行试排并返回完整结果；不存在返回404，已知班次内无可用位置或输入不满足约束返回409。失败不编造交期、也不覆盖旧成功结果；“未找到可用时段”不等于证明全局无解。
- JSON：包含 request_id、基线版本/指纹、事件版本、工具版本、创建时间、资源指纹；summary 包含完成时间、交期判定、受影响数、延期加重数、所有原订单延期对比；details 包含原订单及插单工序设备分配、实体模具、开始/结束、加工时长、换型开始/分钟、固定状态，以及完整加工预估/工艺/资源快照；assumptions 说明模型范围。
- 持久化：复用三表结构中 insertion_requests.assessment_json 保存最新一次完整结果，并更新 updated_at；本步不新增业务数据表，不改变 pending_approval 或审批记录、不发布 current_plan。事务内核对当前正式计划、事件版本和 production_inputs 指纹，计算期间变化则拒绝保存，保留旧结果。GET 待审批列表带 assessment 与 assessment_stale，计划、事件或生产资源变化会标记过期；重新试排替换最新结果。
- 前端：下方待审批列表展开“查看需求”，点击“评估插单”；有结果可重新试排。业务员顶部“试排影响摘要”显示所选已保存申请的真实指标，可展开延期明细；列表按钮“查看试排摘要”切换申请。刷新后自动恢复列表中的已保存试排。计划员在现有工作台看同一申请的摘要与“设备与工序排布明细”。保留纵向布局与原文提示；表单编辑不会把其他已保存申请的试排结果冒充当前草稿结果。
- 代码定位：领域计算在 domain/insertion.py；固定资源在 scenarios/insertion_demo.py；application/sales_requests.py 负责协调和过期判定，仓储端口在 application/ports.py，SQLAlchemy 保存及最终版本检查在 infrastructure/insertion_repository.py；bootstrap 注入工艺和资源工厂。前端 AssessmentView、PendingRequestsPanel 在 features/sales，通过既有 workbench/api.ts 请求，计划员页面通过功能公开入口组合。
- 自动验收：后端385项、前端55项测试通过。新增精确固定案例覆盖“按期且无新增延期”“按期但原订单延期加重”“无法满足要求交期”，同时覆盖固定在制工序、实体模具跨设备串行、班次无解、三条演示工艺的确定性、完整结果落库与重启恢复、无Agent调用、计划不变、事件/资源过期与计算期间事件变化拒绝覆盖。前端验证宏观/设备明细的分角色渲染、刷新恢复、过期提示和试排失败。两端格式/架构与构建检查通过。
