# 紧急插单申请记录改造（2026-10-26）

## 管理者插单申请审批

管理者区块改名为“插单申请审批”，默认展示全部已提交申请（待审批、已批准、已驳回、已发布），不展示草稿。待审批优先，同组按记录创建时间倒序；状态筛选与现有日期筛选组合生效。表格增加申请业务员、要求交期与提交时间，时间使用北京时间。

全部记录复用现有详情抽屉，历史记录只读，只有待审批记录提供批准和驳回操作。审批成功后重新读取列表和详情，默认全部状态下保留该记录并展示新状态；选择待审批筛选时，已审批记录退出当前筛选。复用现有接口，不修改数据库或审批、发布约束。

## 确认范围

业务员优先跟踪申请：申请记录置于表单上方，卡片每页 5 条，按提交时间倒序；新建插单定位并聚焦表单。统一使用“查看详情”，提交成功后可直接打开该申请，详情继续使用现有抽屉。

卡片展示编号、产品、数量、要求交期、状态及四个节点：试排评估 → 提交管理者审批 → 管理者审批 → 排产员复核发布。完成勾选、当前高亮、后续置灰；驳回终止、过期需重新试排。旧记录无有效试排时仍高亮试排节点，不将待审批误报为已评估。审批通过不等于已发布。

业务员在填写区点击“评估插单”，先通过创建接口的 `draft_only=true` 保存草稿，再执行现有四角色评估并展示摘要。草稿不创建审批记录，也不进入管理者和排产员的待办列表。评估完成后点击“提交管理者审批”，通过 `submit` 动作绑定 assessment_id；后端事务内核对计划、事件及生产资源指纹，再转为 pending_approval 并创建审批记录。修改填写内容后清除旧摘要与提交资格，重新评估会保存新的草稿。详情保留重新试排入口，批准与发布规则保持原约束。

兼容旧调用：创建接口省略 `draft_only` 时仍按原流程保存为 pending_approval；新版业务员页面固定传 true。新 `submit` 动作不接受缺失、错误或过期评估。数据库已有 draft 状态，无需新增结构迁移，也不清理旧记录。

## 插单评估实时链路

填写区和申请详情中的评估入口请求 `Accept: application/x-ndjson`，复用现有流式传输。`InsertionWorkflow` 在实际角色执行前后发送开始、完成或失败事件，页面展示数据校验 → 排产试算 → 方案评估 → 结果解释 → 保存评估结果。角色工具和适用模型辅助均完成后才标记该角色完成；规则、模型辅助和降级模式如实显示。保存失败、角色失败或连接中断时保留已完成节点，未执行节点不标记成功；只有取得最终结果并恢复权威记录后才允许提交审批。不使用计时器模拟进度。普通 JSON 客户端保持兼容。

## 姓名与兼容

新申请由服务端固定记录演示业务员 ID `sales_01`，与 `planner_01` 的演示身份口径一致；单独持久化在 nullable 的 `applicant_id` 中，不复用姓名或会话字段，也不接受客户端指定。详情优先展示 ID，旧记录没有 ID 时保留已记录姓名或显示“未记录”。旧库通过备份后加列兼容，不回填历史身份。该 ID 是演示标识，不代表已实现账号认证。

详情在提交时间附近显示“申请业务员”。当前只有演示角色，没有可信姓名来源；新增 nullable 的 applicant_name 保存字段，缺失显示“未记录”，不把角色或 session_id 当作姓名，不接受客户端冒充认证姓名。后续接入真实身份时由应用层写入提交时姓名快照。本次不增加账号系统或姓名手填入口。

旧 SQLite 数据库通过加列兼容，迁移前复用现有备份机制；不回填猜测姓名，不重置业务数据。新旧记录均可读取。

## 能力边界与验收

紧急插单现有试排失败返回错误，不持久化无候选 assessment；保留真实错误提示，不由前端推断或伪造“无可行候选”业务状态。卡片不能把失败当作评估完成。未来提供结构化无候选结果时再接入节点显示。
