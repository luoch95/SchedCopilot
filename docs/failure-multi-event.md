# 多设备故障并行处理

## 背景

当前故障模型只有一个 `current_event`。新保存的设备故障会成为最新修订，页面再把其他修订统一显示为历史故障。这把“最新记录”错误地当成了“唯一未完成故障”，无法表达 M1、M2 同时处于处理中的场景。

## 业务规则

- 每次打开录入窗口和修改字段都只是草稿，不生成事件身份或业务编号。
- 只有保存通过校验并成功持久化后，才创建故障事件记录并生成稳定的 `fault_event_id` 与业务编号。
- 取消、关闭、校验失败或保存失败不得改变已保存事件的业务编号。
- 故障事件以稳定事件身份关联设备、时间、分析、审批和发布记录；`event_revision` 只用于内部快照并发校验和旧数据兼容。
- 多个设备故障可以同时存在；新保存的故障不得自动关闭或历史化旧故障。
- 故障是否为历史记录由流程状态决定：已发布、已撤销或已关闭才进入历史；登记中、分析中、待审批、已审批待发布均保留在待处理区域。
- 业务员工作台和管理者审批页使用同一套事件状态语义；管理者按事件分别查看审批信息。
- 页面展示业务编号格式为 `{设备}-GZ{当天序号}-{流程节点}`，例如 `M1-GZ01-001`；流程节点推进只改变末尾三位，不改变事件身份和设备当天故障序号。

## 当前实现边界

本轮先统一事件状态字段、历史筛选和角色页面展示，确保未完成的旧故障不会因新故障保存而显示为历史。事件分析、审批和发布接口仍须以具体事件身份为边界；不得用全局“最新修订”替代事件身份。

## 验收示例

1. 打开录入弹窗并填写 M1，关闭弹窗，事件修订号不变。
2. 保存 M1 后生成 `M1-GZ01-001`，显示为故障登记中。
3. 保存 M2 后生成 `M2-GZ01-001`，M1 仍显示为故障登记中，M2 也显示为故障登记中。
4. M1 完成发布或撤销后，M1 才进入历史；M2 的状态不受影响。
5. 业务员页和管理者页对 M1、M2 的状态判断一致。
## 新版故障业务编号与状态规则（V0）

页面展示 `M1-GZ01-001`：设备编号、设备当天故障序号、当前流程节点。`fault_event_id` 是内部稳定主身份，绑定分析、候选、审批、撤销和发布；`event_revision` 仅保留为快照并发校验和旧数据兼容字段，页面不再展示旧 R 编号。

设备当天序号按中国业务时区独立递增，不同设备分别计数，跨日重新从 `GZ01` 开始。同一设备、同一故障开始时间的修订复用同一事件 ID 和业务编号，流程推进只更新末尾节点。

登记中、分析中、待审批、已审批待发布均是未完成状态；已发布、已撤销、已关闭才进入历史。新增其他设备故障不会改变已有事件状态或卡片颜色。业务员与管理者页面使用同一状态语义，事件操作按 `fault_event_id` 绑定。旧 R 数据保留并在启动时补齐映射，不清空业务数据。

## 故障方案可视化补充（2026-10-27）

- 等待与设备转移候选统一按同一基线逐工序比较开始时间。未完成工序开工推迟时保留红框，仅在悬浮详情中以红色字体显示“顺延 × 分钟”，甘特图上不显示顺延文字，转移保留设备转移信息。已完成工序不因同订单其他工序变化而标红。
- 工序顺延与订单交期逾期分别表达。绿色方案仍可包含顺延工序。
- 工序详情当前时间段加“评估方案 ·”，原安排补齐开始与结束时间。
- 换型总时长展示次数乘单次时长，范围为整个候选计划全部设备（含已完成工序及初始模具切换），并保留分设备数据；缺项仍显示未计算。
- 故障决策页使用服务端故障业务编号及流程节点，不显示事件 R 修订；报告和人工草案版本明确标为“第 × 版”。内部事件修订及计划 V 版本校验保持原有语义。


## 管理者审批详情按需加载（2026-10-27）

- 工作台概览保持精简，不携带完整分析、工作流及结论正文。
- 打开“审批详情”时调用 `GET /api/fault-reviews/{review_id}`，读取该审批持久化的评估快照，呈现方案对比、甘特图、评估报告与 Agent 链路；无候选审批呈现结论、依据与限制。
- 不使用当前最新分析替代已提交审批的分析；后续生成其他方案及重启服务不改变原审批详情。
- 加载期间、读取失败、记录缺失或快照不匹配时禁用审批，错误提供重试；最终审批仍由后端检查当前计划和事件约束。

## 发布后的故障编号补齐（2026-10-27）

- 排产员和管理者的已发布卡片统一展示业务编号与发布节点，例如 `M1 停机 · M1-GZ01-004 · 已发布 V1`；历史卡片和分析详情标题不再拼接 R 修订号。
- 历史发布快照缺少编号时，按稳定事件 ID 关联；无 ID 的旧快照仅在修订、设备及故障开始时间一致时关联。保留存档的故障时间和指标，不借用其他故障的编号。
- 无法关联的记录明确显示“编号缺失”，不生成虚假故障序号。内部修订及计划版本校验保持原有语义。

## 已发布计划概览缺失明细的兼容（2026-10-27）

概览接口的 `fault_traces` 不包含 `affected_operations`；该字段仅在完整分析中提供，前端契约应标记为可选。执行计划甘特图保留已发布故障窗口，对缺失明细进行显式处理，不能直接读取其长度导致白屏，也不能将缺失视为全部转移或已核实避开停机窗口。无当前冲突且缺少明细时提示查看历史 AI 分析。回归覆盖概览仅含发布版本及故障窗口的场景。

概览中的当前故障已发布状态同时依据同计划版本、同事件身份及修订的发布留痕识别；不依赖被省略的完整分析。不从留痕补造基线版本或可发布候选，卡片指标复用留痕的已有指标，详情仍按需加载。

### 已发布方案详情按需加载

工作台概览只返回故障发布摘要，不保证携带完整分析。排产员进入已发布故障的“故障影响与方案决策”页时，按事件修订读取 `/api/events/{revision}/analysis`，核对事件修订及发布版本后展示历史候选、甘特图和评估依据。加载中、请求失败、存档缺失或不匹配时明确提示，不能回退到“尚未生成”或开放生成、审批及发布操作。历史候选只用于查阅，不写入当前评估控制器。
