# 动态编排器

动态编排器采用确定性路由和结构化共享状态，支持四类意图：

- `generate_candidates`：校验 -> 排产 -> 评估 -> 解释
- `re_evaluate`：基于已有候选重新评估
- `explain`：解释已有结果
- `validate`：只执行数据校验

各 Agent 只通过编排器通信。结果和工具新生成的证据合并到 `evidence_catalog`，下游通过引用读取。Agent 返回 `blocked` 或 `failed` 时停止依赖路径；校验阻断允许追加一次原因解释，整体仍保留阻断状态。排产或评估失败时不再调用依赖节点。

编排器限制最大步骤数，并记录执行 trace；完成、警告、阻断、失败的节点均不重复执行。调用前检查请求、结果和证据是否属于同一快照，异常仅暴露可识别错误码。

## API 与页面

`POST /api/workflow` 接收 `event_revision`、`baseline_fingerprint`、`intent`、`question`，重评估和解释还需传入上次响应的 `workflow.id` 作为 `workflow_id`。响应包含 `workflow`（状态、执行记录、四角色结果、证据目录）及 `simulation`（完整成功链路产生的服务端候选批次，其他路径为 null）。未知意图或不存在的工作流返回 422，过期快照返回 409。

前端只保留一个“生成候选方案”按钮，调用完整四 Agent 工作流。确认操作意图后先展示本次链路：生成候选显示校验 → 排产 → 评估 → 解释，独立校验、重评估、重新解释只显示对应节点。节点用箭头连接，后台实际执行的节点显示“执行中”和脉冲动画，其余显示等待；完成后显示结果摘要、模型辅助或规则回退，并可点击“查看详情”展开、聚焦对应报告。支持键盘操作、窄屏布局和减少动态效果偏好。

请求头 `Accept: application/x-ndjson` 启用同一 `POST /api/workflow` 的流式响应，依次发送 `plan`、真实 Agent 调用前的 `stage_started`、结果记录后的 `stage_completed`，最后发送 `result`（原完整响应）。长调用期间发送 `heartbeat` 维持连接，不用时间推算进度。业务异常通过 `error` 事件保留错误码和状态码，初始请求结构错误仍按 HTTP 校验返回；普通 JSON 客户端保持原响应协议。Vite 代理已用于验证逐条返回；其他反向代理部署时也须关闭响应缓冲。

校验阻断后仍可执行解释 Agent，排产和评估标注未执行；工具失败不会继续依赖节点。连接中断时前端保留已收到的结果，将其余节点标为“状态未确认”，不自动重试；后台正在执行的同步模型调用可能继续，但不会自动发布。只有完整结果通过最终快照检查后，前端才接收可用候选。“执行详情”仍收纳各节点问题、调用记录、仅校验和重新评估操作。未知恢复时间时可单独校验，不会产生候选。

评估警告和缺失指标进入“方案比较”，解释 Agent 的事实、假设、风险、取舍进入“辅助分析”。重新解释只读取同一工作流结果；重新评估清除旧解释，提示用户重新解释；重新校验会清除本次候选。新候选继续使用原有人工发布流程，发布请求只包含服务端批次及候选 ID。

现有 `/api/simulations` 和 `/api/analysis` 后端接口保持兼容，前端不再调用。旧三角色模型分析区域与模型开关已从页面移除；辅助分析统一展示解释 Agent 的结果。V1.2 已将真实模型接入四角色主流程：模型调用角色工具并根据问题选择证据重点，完整规则报告仍保留；页面标注模型辅助或规则回退。配置与执行信息见[模型接入说明](live-model-integration.md)。

## 数据与运行边界

- 缺少实体模具时保留空记录和未检查项，不从设备能力表伪造模具。
- 缺少换型、班次数据时返回明确警告、缺失指标列表及 null 换型指标，不计算虚构利用率。
- 事件编辑、重新载入或正式发布后，页面清除旧工作流；服务端在执行前后核对快照。
- 工作流会话暂存在单进程内存中，最多保留 32 次结果；重启或淘汰后需重新执行。适用于当前本地演示，多进程部署前需增加持久化会话。候选和人工决定仍使用现有 SQLite 存储。

测试覆盖完整链路、校验阻断解释、独立意图、重复执行、工具异常、过期上下文、证据连续性、步数上限、HTTP 重评估与人工发布，以及页面的警告展示和编辑失效。

流式链路验收：后端 315 项、前端 32 项测试通过，前端构建、架构边界及格式检查通过。通过当前 5173 端口的 Vite 代理执行一次真实模型链路：约 0.02 秒收到校验开始，9.06 秒校验完成并开始排产，38.08 秒排产完成并开始评估，65.50 秒评估完成并开始解释，79.81 秒收到完整结果；四节点均为 `live/success`，生成两个候选，工作台执行前后完全一致。该次浏览器视觉验收受工具连接错误阻碍，未宣称通过。

## 补充仿真演示数据

在仓库根目录执行 `uv --directory backend run python -m sched_copilot.seed_demo`。
脚本先备份已有 SQLite 数据库到同目录 `backups/`，再向空的生产资源快照插入数据；重复执行不覆盖已有输入，也不修改正式计划、事件或人工决定。

数据明确标记为仿真：8 个实体模具、11 道工序的模具分配、3 台设备的双班日历（08:00–24:00）、初始装模，以及不同模具换型 15 分钟。
新候选遵守班次、换型间隔、故障窗口和实体模具占用；评估展示实际换型次数、分钟及班次利用率。利用率口径为 `(加工分钟 + 换型分钟) / 扣除故障的班次可用分钟`，不是实时设备 OEE。

未导入数据时继续返回缺失指标与警告，不补假零。导入后刷新页面并重新生成候选；旧工作流的资源指纹将失效。物料、人员和模具保养仍属于未检查项，故障恢复仍是人工估计，必须保留风险说明。

已用当前运行的后台验证完整四节点、两个候选、重新评估和解释；人工发布闭环在隔离测试数据库验证，当前正式计划不自动发布。

## 等待恢复与正式计划对照

“原设备等待恢复”保留正式计划的设备分配和每台设备的加工顺序，仅按故障、工序依赖、换型和班次等约束顺延。交期优先规则不能在该策略下让后续工序插到原队列前面；允许转移策略仍可重新选择设备和顺序。

正式计划保留已发布时段，旧演示计划没有预留全部换型间隔，因此未故障设备也可能因补入换型而顺延。生成候选不会自动覆盖正式计划。方案比较的首张图名称保留“原计划对照”，内容为原设备等待恢复、按生产约束顺延后的实际候选排产；副说明明确其尚未发布，可以参与候选指标比较和人工发布。转移方案显示在其旁边。候选图不再叠加原位置虚线框，工序对照与聚焦提示提供具体调整依据。换型与模具、班次原因随候选保存，不能在编排器转换时丢失为泛化的“策略调整”。

当前允许转移策略会重排全部待加工工序，按最早开工时间选设备，相同开工时间才优先保留原设备；尚未限制未受故障影响工序的设备迁移。例如 M3 故障场景中 O1002-OP1 在 M1 换型后 13:15 可开工，而 M2 可以在空闲期间提前换型并于 13:00 开工，规则因此选择 M2。该转移是规则选择，不能描述为 M1 故障所迫。

每次设备转移都记录原设备是否为故障设备、当次排程状态下两台设备最早可行开工时间，以及相对留在原设备提前的分钟数；原设备无可行时段时明确说明，不虚构收益。说明进入变更证据、工序对照、影响链和解释 Agent 事实。
