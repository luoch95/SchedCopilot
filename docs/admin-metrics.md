# 研发统计后台

直接访问 `/admin`，使用服务端 `SCHED_DEMO_ADMIN_PASSWORD` 对应的演示密码登录。
会话使用 HttpOnly Cookie，退出后统计接口拒绝访问。该入口没有正式账号、角色认证或生产权限体系，
不能作为安全管理员后台对外承诺；生产管理角色选择与前端“解锁”不会授予此后台访问权限。

- `GET /api/admin/metrics`：需要服务端演示会话，返回累计业务统计和本周逐日趋势。
- `GET /api/reports/weekly`：与现有业务只读接口一样可访问，返回北京时间本周一零点至请求时的汇总，
  供管理者驾驶舱下载 Markdown 周报，不返回业务明细。
- 两个接口均通过 SQLite 只读连接在同一事务快照读取，不初始化、迁移或更新业务数据库。
  读取失败时返回错误，不伪装为零。

访问量为真实每日 IP UV：先取 `X-Forwarded-For` 中第一个有效 IP（首项非法则回退），
没有时使用 `request.client.host`；IPv6 统一格式，IPv4 映射地址按 IPv4 计数。
北京时间每天按 IP 去重，累计值为各日 UV 之和；同一 IP 跨日会再次计数，不等于真实人数。
后台显示累计值，周报接口仅返回本周值。角色占比仍为明确标记的 Mock。

前端加载时发送 `GET /api/visits`（204、禁止缓存），因此 Vite 开发环境及 Nginx 静态托管也能记录。
中间件只记录成功的页面 `/`、`/admin` 和该访问请求；不统计轮询、资源及健康检查。
启动时仅新增 `daily_visitors` 表，以 `(visit_date, ip)` 唯一键处理并发去重，不修改业务表。
从更新后开始积累，无法恢复历史访问。原始 IP 仅存于数据库，不返回统计页面；写入失败记脱敏日志，业务响应继续。

按当前约定信任 XFF 首项，直接暴露后端或允许客户端自带 XFF 会被伪造，不能作为防刷或审计依据。
后端应只监听 `127.0.0.1:8000`，公网经受控 Nginx 进入；若需要抗伪造，需另行定义可信代理链。

业务指标口径随接口的 `limitations` 返回，并写入导出的周报：

- 生成：成功产出候选的故障工作流批次；不计校验、重评、解释和无候选结论。
- 采纳：已批准的可执行故障方案与插单申请；批准无候选评估结论不计入。
- 发布：`decisions` 中的真实 `publish` 记录；审批不视作发布。
- 风险拦截：校验禁止生成候选或得出无可行候选的分析次数，不代表去重后的风险数。
- 失败：工作流 `failed`；业务阻断不计为系统失败。
- 降级：一次工作流内真实 `fallback` 最多计一次，主动规则模式、模拟故障不计入。
- 场景热度：设备与故障起始时间去重后的事件记录数（排除系统初始化示例）、插单申请数。

插单现有评估快照缺少评估时间且会被覆盖，不能恢复完整生成、失败、降级次数，
因此不纳入上述调用统计和趋势。采纳率缺少同批次完整历史，返回 `null`；
产能节省没有统一确定性口径，返回 `null`。页面和周报显示“未统计”，不补零或虚构收益。
业务累计数据可跨周，因此本周的发布数与生成数没有比例关系。

## Nginx 与代码更新

[Nginx location 示例](../deploy/nginx-locations.conf.example) 包含 `/` 与 `/api/` 两处代理头，
合并进已有 `server`，保留现有域名与 TLS。示例由 FastAPI 提供前端产物，`proxy_pass` 不带尾部 `/`，保留 `/api/` 路径。
若现有 `/` 使用 `root` / `try_files` 静态托管，可以保留；代理头只在代理请求时生效，前端访问请求仍经 `/api/` 记录。
修改后执行 `sudo nginx -t`，通过后再 `sudo systemctl reload nginx`。

本地验证：启动前后端后打开页面，同一 IP 反复刷新只增加一次；用不同 XFF 调用
`GET /api/visits` 可验证不同 IP，登录 `/admin` 查看累计 UV。不要拿此测试对公网灌入伪造 IP。

更新服务器代码必须遵循 [部署清单](../skill/deploy_skill.md)，此处不代表已部署。
本地 PowerShell 先完成测试与构建，经授权发布代码；不要上传本地 `.data`、`.env`、数据库或虚拟环境。
服务器 Bash 按以下顺序操作，任何失败即停止：

1. 核对目标分支/提交与服务器工作区，按部署清单核验真实进程的
   `SCHED_DB_PATH=/opt/schedcopilot/.data/injection_molding.sqlite3` 和 `SCHED_DEMO_MODE=0`。
   演示模式可能在启动时重置数据库，不能仅检查路径。
2. 记录计划、事件、审批状态；停止服务并按部署清单一致性备份 `.data`、配置和旧前端产物。
3. 在 `/opt/schedcopilot` 使用 `git pull --ff-only` 更新已确认跟踪的发布分支（不强制 reset）；
   确认数据库及 `.env` 未被 Git 跟踪。不覆盖 `.data`、`.env`、`backend/.venv`，不调用演示重置接口。
4. 需要时运行 `uv --directory backend sync --locked`；在 `frontend` 运行 `npm ci` 和 `npm run build`。
   若上传产物，先在独立目录检查排除项，再仅替换明确的代码目录及完整 `frontend/dist`。
5. `sudo systemctl start schedcopilot`；新版本自动新增访问表，保留已有业务数据。
   核对真实进程配置及数据库路径，按部署清单完成“服务器数据库 → 服务器本机 API → 公网 API”一致性验收，再验收页面。
